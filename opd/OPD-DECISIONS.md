## Free-tier constraints (owner FYI, 2026-11-11) — binding on all phases

Supabase Free: **2 active projects per organisation**, 500 MB DB + 5 GB egress
per project, 50k MAU, 500k Edge invocations/mo, **projects pause after 7 days
of inactivity**, no automatic backups. Consequences adopted:

1. **Topology:** every clinic owns its OWN free org/project and hands URL +
   publishable key through the onboarding Connection step (E3). The master
   org holds exactly two: Central + one P0 scratch. The 2-project cap never
   binds the SaaS owner, only per-clinic.
2. **Pause mitigation:** `workspaces.keep_warm_at` shipped in schema v5; a
   Central-side daily zero-side-effect probe (the F5 warm probe) counts as
   tenant activity. Client must render a clear "clinic database asleep —
   restore in Supabase dashboard" state on the paused-tenant error, never a
   generic failure. Restore runbook goes into the operator docs (P8).
3. **No backups:** per-tenant export runbook (scheduled pg_dump via CI or
   Management API) is a P8 deliverable; recommend Pro per clinic once revenue
   allows. Data-loss risk recorded, not hidden.
4. **D1′ on free:** projects created since Oct 2025 issue asymmetric JWTs
   with a public JWKS by default, so the RS256/JWKS path is plan-independent.
   Configuring *third-party auth* on tenant projects remains the one P0
   verification item; designed fallbacks if a tenant cannot trust external
   JWKS: (a) Ed25519 capability token in a custom header, verified inside
   tenant RLS via pgsodium (zero platform config, any tier), (b) shared
   HS256 secret (last resort).
5. Master on free is comfortable at pilot scale: discovery + licence RPCs
   are small payloads; 5 GB egress ≈ tens of thousands of boots/month.
